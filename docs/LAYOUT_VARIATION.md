# Seeded world-layout variation (layout v2)

_2026-10-20, updated by the phase 2 hardening pass (see "Phase 2 hardening" at the end)._

> [!NOTE]
> **Release note.** This is the design record of layout v2, written while it was experimental.
> Since then the identity-conflict development matrix (294 missions,
> [`experiments/identity-conflict/`](experiments/identity-conflict/)) has used layout v2. The held-out
> results in [`RESULTS.md`](RESULTS.md) and the Lab still use layout v1. Commit hashes and "phase"
> reports mentioned below refer to the development history and are not part of this repository.

## Root cause

In the original layout (now called **v1**), the seed hardly changed the world.

- **Fixed slots.** `src/scenarios/layout.ts` puts every object in a fixed slot, and the seed adds
  only a small jitter:
  - plant: ±0.3 m;
  - poster: ±0.3 m along the north wall;
  - screen: ±0.25 m along the interior wall;
  - furniture: ±0.05–0.2 m.
- **Small changes elsewhere.** The robot start moves by ±0.2 m and ±10°. The lighting and the
  sensor noise also follow the seed.
- **Same furniture everywhere.** All seven scenarios use the same furniture set in the same places.

So seeds 0 and 17 give nearly the same room. The mean object displacement between them is under
1 m in every scenario; a unit test checks this.

## Design

- **v1 stays unchanged.** It remains the default wherever recorded data is involved: the batch
  engine, the Lab, `/diagnostics/mission`, the Lab "Replay" links (`&layout=v1`) and the README
  reproduction commands.
- **v1 is pinned by a test.** `tests/unit/layout.test.ts` compares v1 against a golden snapshot
  taken before any change: 7 scenarios × 8 seeds, including evaluation seeds 1001 and 1020.
- **Which layout a Mission Control URL opens** (`src/console/params.ts`):
  - a fresh visit (no scenario, seed or method in the URL) opens v2;
  - `layout=v1` or `layout=v2` opens that layout;
  - a link with scenario, seed or method but **no** `layout` opens v1, the layout every such link
    was made for. It shows a notice and rewrites the address to say `layout=v1`;
  - any other `layout` value (for example `v3` or `V2`) is refused: no world is built and the page
    explains why.

  `/diagnostics/mission` keeps v1 as its default when `layout` is absent and refuses unknown
  values.
- **v2 generator.** v2 is generated by `generateLayout(scenarioId, seed)` in
  `src/scenarios/generate.ts`.

### What v2 varies

| Element | Placement |
|---|---|
| Target (plant) | East room. 5 zones: north strip, east wall, centre, south-east, north-west corner |
| Framed print | Any west-room wall: north, interior, west or south |
| Display on cabinet | Any west-room wall |
| Photo board, vase | 4 west-room floor zones. The board turns its face towards a nearby stretch of the route |
| Occluding crate | 0.95–1.8 m in front of the plant, on the line to the first route pose that would see the plant |
| Sofa, chairs, pouf, crate | Each piece on any of 4–5 wall or floor zones in either room |
| Robot start | 3 start zones in the west room; heading uniform over 360° |
| Lighting | Light scale 0.8–1.15 (same range as v1); sun azimuth 0–360° |

### What v2 keeps

- **The object set.** Ids, kinds, labels and models are each scenario's own. v2 re-places them and
  never adds or removes any.
- **Scenario semantics.**
  - Decoys and look-alikes stay in the west room and the target in the east room, as the scenario
    summaries say.
  - `decoys-only` has no target.
  - Decoys are met before the target along the route.
  - In `occluded-target`, the crate hides the first route view of the plant.
- **The fixed search route.** It is robot prior knowledge, so v2 keeps objects clear of it instead
  of changing it.

### Determinism and streams

- **Independent streams.** Each part of the layout uses its own seeded stream,
  `mulberry32(deriveSeed(seed, "<scenario>#layout-v2#<attempt>#<stream>"))`, for these streams:
  - `semantic`: target, decoys and occluder;
  - `furniture`;
  - `start`;
  - `light`. This stream does not depend on the attempt number, so a retry changes only the
    geometry.
- **No other randomness.** There is no `Math.random()`, no clock and no map or set iteration in
  generation.
- **Bounded retries.**
  - Each object gets up to 30 placement tries per attempt.
  - With an occluder, the generator tries up to 8 target positions per attempt.
  - Each layout gets up to 32 attempts. If none validates, the deterministic fallback is the v1
    layout. It is flagged in three places that cannot disagree: the id (`v2-fallback-<hash>`),
    `fallback: true`, and its own validation result (`valid`, `failedChecks`). A fallback is never
    reported as a validated v2 layout.
- **Recorded identity.** `layoutRecord()` (in `generate.ts`) is the single place a layout becomes a
  record. It refuses an id/flag contradiction, or an unvalidated non-fallback v2 layout.
  - Diagnostics batches: `RunRecord.layout` = `{version, id, attempt, fallback, valid, failedChecks}`,
    present for v2. It is absent for v1, which keeps the historical file format.
  - Console export: `layout` uses the same record.
- **Layout id.** The id is `v2-<FNV-1a hash>` of the rounded object poses, start and lighting.

### Ground-truth isolation

- **No import path to the robot.** `generate.ts` and `validate.ts` are ground-truth modules.
  Robot-facing modules (`verify`, `policies`, `sensing`, `perception`, `mission`) do not import
  them; the existing isolation unit test covers this.
- **Unchanged robot inputs.** The robot still gets only:
  - the occupancy prior map, built by the unchanged world builder from object meshes;
  - the fixed route;
  - its start pose;
  - rendered RGB-D frames.
- **Layout data stays outside the runner.** The layout id and zones never reach `MissionRunner`.
  The console shows only a non-revealing summary before a mission: object count, start pose and
  light scale. A unit test checks that the summary contains no object id, zone name or object word.
  The per-object zones appear only in the Evaluator panel after the mission ends. They are held in
  the console's UI state from the moment the world is built, which page JavaScript can read; the
  robot cannot.
- **Test hook.** `ConsoleController.gridCheck()` is a test hook on the UI side. It compares the
  validator's map with the built world's grid. It is never passed to the runner.
- **Unchanged verification.** The verifier, thresholds, evidence rules, detector and mission
  termination logic are untouched. Decoy rejection still comes only from the depth evidence.

## Validation (`src/scenarios/validate.ts`)

The validator rebuilds the prior map the world builder makes: walls, plus every non-poster
footprint as the rotated bounding box, inflated by 0.32 m. It then runs the real A* planner on that
map. A v2 layout is accepted only if every check passes.

**One visibility model.** Visibility of an object is a 2-D ray on the raw occupancy grid built
**without that object** (`buildSightGrid(objects, [o])`, `objectVisible`). Its own footprint never
hides it, and every other footprint, however close, can. A wall print's look point sits inside the
wall's grid cells, so its ray stops 0.15 m short. The same model is used by:
- the observability check;
- the occlusion check (the first pose that sees the plant with the crate removed must lose it with
  the crate present);
- the generator's occluder placement;
- the fake sensor of the geometric mission test.

Before phase 2, observability skipped the last 0.6–0.8 m of the ray, while occlusion tested the
full ray against the crate rectangle. A unit test shows a crate 0.45 m in front of a plant is now
treated as blocking it.

`verificationViewpoints` deliberately keeps the robot planner's own 0.8 m allowance, because it
models what the robot's planner will do, not what is visible.

| Check | Rule |
|---|---|
| `inside-walls` | Footprints are inside the rooms and do not cross the interior wall; prints sit on a wall face |
| `no-overlap` | Floor footprints are ≥ 0.05 m apart; prints do not overlap each other or a display |
| `start-free`, `waypoints-free` | The start and all 9 route waypoints lie in free space |
| `route-astar` | A* plans every route leg in order; the route is simulated as the runner drives it (a frame every 1 m facing the direction of travel, plus the scan headings) |
| `observable-from-route` | Each target, decoy and look-alike is in view from at least one route pose: range 1.6–5.5 m, within ±27.8° of the heading, clear 2-D line of sight, and pictures facing the camera within 60° |
| `target-verifiable` | The target has ≥ 3 planner-ring viewpoints (1.9 and 2.2 m rings, 30° bins) that are free, have line of sight and are A*-reachable, spanning ≥ 60° of bearing |
| `target-approachable` | A 0.9 m stand-off point is A*-reachable |
| `decoys-reobservable` | Each decoy has ≥ 2 reachable verification viewpoints |
| `scenario-semantics` | Target present or absent as the scenario requires, at most one target, decoys **geometrically** in view before the target, and the crate hiding the target's first view (same visibility model) |

**Geometry is not perception.** `observable-from-route` and the "decoy before target" rule say an
object is inside the camera's field of view and range, unobstructed in 2-D, and facing the camera.
They do not say COCO-SSD will detect it. In the real-render smoke test, 3 of 18 target-present
decoy layouts never produced a decoy track (see "Real missions").

The generator also keeps:
- the route corridor clear: ≥ 0.45 m from every route segment, or 0.38 m for the occluder;
- ≥ 0.75 m around waypoints;
- ≥ 0.6 m around the start;
- the doorway clear;
- 1 m of floor clear in front of each wall print.

### The validator on v1 (finding, not fixed)

Run on the recorded v1 layouts, the validator flags two existing problems.

- **The pouf blocks route waypoint 8 in many seeds.** Its random yaw enlarges its axis-aligned
  footprint up to (1.6, 3.6). In the recorded held-out data, **34 of 560 runs logged "waypoint 8
  unreachable; skipped"**. 23 of these are in `decoys-only`, where the robot searches to the end
  of the route.
- **The two chairs touch in some seeds.**

v1 is left exactly as it was, because the recorded results depend on it.

### Validator map vs the world builder's grid (phase 2)

`tests/e2e/hardening.spec.ts` builds real worlds in the browser and compares the validator's
analytic map with `world.grid`, the map the robot actually navigates on, cell by cell. The world
builder makes it from runtime `Box3` bounds of the GLB meshes. The test covers the 7 scenarios ×
v2 seeds 0, 17, 42 plus v1 seed 0: every asset (plant, vase, both chairs, sofa at 0/90/180/−90°,
pouf, crates, screen, photo board) at seeded yaws.

- **Occupied in the world but free in the validator's map:** 0–9 cells per world. Every one is
  within 1 cell (0.1 m, the grid resolution) of a cell the validator marks occupied: a boundary
  quantisation, not a missed object. The same holds for the robot-centre (inflated) mask.
- **Occupied in the validator's map but free in the world:** 0–50 cells. The validator is
  conservative here (rotated whole-object boxes and rounded sizes).
- **Every navigation check passes on the real grid** for all 21 v2 worlds: start, waypoints,
  every route leg by A*, verification viewpoints and stand-off.
- **v1 on the real grid.** For clear-target and poster-decoy seed 1001 the real grid fails
  `waypoints-free` and `route-astar` (waypoint 8). This matches the pouf finding above and the
  recorded "waypoint 8 unreachable" events.

**v1 regression with real missions.** I re-ran the README's held-out-evaluation commands with
`SEEDS=1001` (7 scenarios × 4 methods = 28 missions) against a production diagnostics build of this
worktree (`npm run build:diagnostics`, `next start`). I then compared the result with
`scripts/compare-runs.mjs` against `public/data/eval-runs.json`.

- **Production build: 28/28 runs identical** to the committed records apart from wall-clock
  timing. Every frame, detector score, decision and evaluator score matched.
- **`next dev`:** the same 28 runs gave identical outcomes, frames, decisions and evaluator scores.
  3 single-frame runs differed only in detector scores in the 4th decimal and in positions at about
  1e-8 m. The README notes 4th-decimal differences of the same kind for console replays. The
  production build of the same code reproduces the records exactly, so the layout change is not
  the cause.

What the new tests cover:
- **Scenario × seed coverage.** All 7 scenarios, discovered from `SCENARIOS`, × seeds 0, 1, 2, 17,
  42, 123.
- **Determinism.** The same seed gives the same objects, start, light and id.
- **Material difference.** Seeds 0 and 17 differ materially:
  - mean object displacement ≥ 1 m;
  - at least one object moves ≥ 2 m;
  - a scenario-defining object moves ≥ 0.5 m;
  - the start differs.

  The same criterion fails on v1.
- **Distinct ids.** The six test seeds give six distinct ids per scenario, and each differs from
  v1.
- **Object set.** It is unchanged.
- **Geometry.** All layouts are inside the walls with no overlaps.
- **Navigation (real A*).** The start is free, every waypoint is reachable in order, and the
  target is approachable.
- **Semantics.** As listed under "What v2 keeps".
- **Broad sweep.** Seeds 0–199 × 7 scenarios (1,400 layouts) validate with **0 fallbacks**.
- **Validator self-tests.** An object on the route, an overlap, a blocked start and a target in
  `decoys-only` are each caught.
- **Geometric missions [geometric]** (`layoutMissions.test.ts`). The real `MissionRunner`, A* and
  policies run on each v2 layout's prior map with a geometric fake sensor. The fake sensor uses the
  validator's own visibility model, so this test checks consistency between the validator and the
  mission loop. **It cannot reveal errors in that model, and it says nothing about perception.**
  - SureStop never has a navigation failure or an unreachable waypoint.
  - It arrives at the real plant in all 30 target-present layouts, excluding the look-alike
    scenario.
  - It ends correctly without arrival in all 6 `decoys-only` layouts.
  - It rejects every decoy.
  - Single-frame stops at the decoy in all 18 decoy-scenario layouts. This shows the geometric
    "decoy first" ordering holds for the fake sensor. It does **not** show that real perception
    meets the decoy first: in 3 of those 18 layouts it never did (see "Real missions").
- **Browser interaction (e2e).**
  - Changing the seed rebuilds a different world without starting a mission; going back to seed 0
    rebuilds the identical world.
  - Changing the scenario rebuilds the world.
  - The v1 switch gives a `v1-` id and adds `layout=v1` to the URL.
  - Step runs one step and then pauses; Reset rebuilds the same layout with no mission.
  - Lab replay links carry `layout=v1`.

**Asynchronous world builds.**
- **Original fix.** Typing a seed such as "123" fires configure(1), (12) and (123), and the world
  builds could finish out of order. `prepare()` is serialised in the engine, and the console drops
  stale builds.
- **Phase 2 additions.**
  - The new selection and the "preparing" phase are published in one state update, with the
    layout id, summary, zones and record cleared and the previous runner withdrawn.
  - A failed build that has been superseded cannot overwrite newer state.
  - `start()` and `step()` refuse unless the built world matches the selected scenario, seed and
    layout (`worldMatchesSelection()`).
- **Pre-existing input bug, now fixed.** The scenario, method, seed and layout controls were
  disabled while a world was preparing, so after the first digit of "123" the next keystrokes were
  dropped. The new e2e test caught it: the field showed "01". These controls now stay enabled while
  preparing; a newer choice supersedes the build in progress.
- **Evidence** (`tests/e2e/hardening.spec.ts`):
  - typing "123" key by key, and three back-to-back configure calls with Run pressed in between,
    both end on seed 123's world, id and objects, identical to a fresh load;
  - no mission started on a stale world;
  - a watcher on every state change saw no "preparing" state with a stale id and no
    "ready/running/done" state whose world differed from the selection.

## Real missions (v2, real rendering and COCO-SSD)

These are 84 missions: 7 scenarios × seeds 0, 1, 2, 17, 42, 123 × SureStop and the tuned
single-frame baseline (τ = 0.9). They were run through `/diagnostics/mission?...&layout=v2` on
`next dev` with headless Chromium, SwiftShader WebGL and TF.js WASM, using the same real rendering
and COCO-SSD inference as the recorded experiments.

- **Raw data.** Preserved in `docs/experiments/layout-v2-smoke/`, with checksums in its
  `MANIFEST.md`.
- **Superseded layouts.** Phase 2 changed the occluded-target layouts for seeds 42 and 123. Their
  4 runs were repeated on the new layouts (`v2-occluded-rerun.json.gz`), and the table below shows
  those runs in place of the superseded ones (marked "phase 2"). The counts below are for the
  current layouts.

- The two batches took 712 s and 571 s of wall time.
- There were 0 console errors in the 84 runs and 0 in the 4 phase-2 re-runs.
- No run had a navigation failure or an "unreachable; skipped" waypoint.

This is a smoke test of the new layouts on a handful of seeds, not an evaluation. No rates or
statistical claims are drawn from it.

**What happened.**

- **SureStop.**
  - Arrived at the real plant in **35 of 36** target-present layouts.
  - The exception is a **false arrival at the vase in `lookalike-3d` seed 123** (`v2-04a6cf82`).
    This is the known limitation that depth cannot reject a 3-D look-alike, but it had **never been
    observed for SureStop**: in the recorded v1 held-out data SureStop had 0/20 look-alike false
    arrivals (only the 1-view ablation had 7/20). The trace is preserved and the issue is open;
    see `docs/LOOKALIKE_INVESTIGATION.md`. The verifier was not changed. In the other 5 look-alike
    layouts the vase was REJECTED (1) or UNCONFIRMED (4).
  - In all 6 `decoys-only` layouts it ended NOT_FOUND with every decoy REJECTED, which is correct.
  - **Decoy never met.** In 3 of the 18 target-present decoy layouts, real perception never opened
    a track on the decoy, although the validator had it geometrically in view before the target:
    - poster-decoy seed 42 (`v2-2805ba1b`);
    - screen-decoy seed 2 (`v2-d291bcb9`);
    - screen-decoy seed 17 (`v2-8f052f46`).

    Those runs were effectively clear-target runs. This was **reproduced in phase 2** on the same
    layout ids with `tests/e2e/perception-decoy.spec.ts` (opt-in, real perception): all three
    again opened only the target track. A control case (poster-decoy seed 0) met and rejected its
    print.
- **Single-frame (τ = 0.9).**
  - 7 false arrivals: at the photo board in all 6 `photo-board-decoy` layouts, and at the print in
    `decoys-only` seed 123.
  - In 10 target-present layouts of the original matrix no "potted plant" detection reached 0.9 in
    any frame (the highest was 0.79–0.89), so the route ended NOT_FOUND. On the 2 occluded layouts
    re-made in phase 2 single-frame also ended NOT_FOUND, so on the current layouts the count is
    12. The detail below is for the original 10.
    - In 6 of these the plant stood 1.3–7.7 m from the v1 slot: on the east wall, in the
      south-east corner or in the north-west corner.
    - In 4 it stood only 0.8–0.9 m from the v1 slot, so a new position is not the only cause.
      Viewing angle, the start pose and lighting also vary in v2.
    - The threshold was tuned on v1 calibration seeds. v2 shows it does not transfer to new
      layouts. This is observed on 10 runs, not measured as a rate.
  - 18 correct arrivals on the current layouts (20 in the original matrix, whose two occluded
    layouts it reached), and 5 correct no-arrival endings.
- **Track on the crate.** In `occluded-target` seed 2, single-frame also opened a track on the
  occluding crate. The detector fired over the crate, and the evaluator labelled the track

## Manual test guide

Start the dev server from the worktree with `npx next dev -H 127.0.0.1 -p 3000`, then open
`http://127.0.0.1:3000/console`.

1. **Default layout.** A fresh visit to `/console` opens *Picture decoy first*, seed 0, with
   *World layout* set to *Seeded variation (v2)*. (The handover version of this guide said
   seed 1. An absent seed has always read as 0.) The line under the selector shows a
   `v2-xxxxxxxx` id, the object count, the start pose, the light scale and "validated". It never
   names an object.
2. **Change the seed.** Select the seed and type 17. The 3-D room rebuilds, with the print on a
   different wall and the furniture moved, and the id changes. The phase returns to READY with 0
   frames; no mission starts. You can keep typing while a room is being built.
3. **Change it back.** Set the seed back to 0. The identical room and the same id come back.
4. **Change the scenario.** Pick each entry in turn:
   - *Decoys only*: no plant in the east room.
   - *Partially occluded target*: a grey crate stands between the plant and the route.
   - *Life-size photo board first*: a board on an easel in the west room.

   Each rebuilds with a new id and no mission.
5. **Switch to v1.** Choose *Recorded evaluation (v1)*. The id becomes `v1-…`, the URL gains
   `layout=v1`, and the room returns to the fixed slots: the print on the north wall and the plant
   in the north-east.
6. **Run a mission.** Pick v2, press **Run mission**, choose Max speed, and wait for DONE.
   - The Evaluator panel appears.
   - "Layout v2-…: where each object was placed" lists the zones.
   - **Export mission JSON** downloads a file named with the scenario, seed, layout id and method.
7. **Run again and Reset.** **Run again** rebuilds the same layout and runs it again. **Reset**
   returns to READY with the same id.
8. **Step.** **Step** from READY runs one step and pauses at PAUSED. **Resume** continues the
   mission, and **Reset** clears it.
9. **Lab replay.** In `/lab`, Inspect any recorded trial. "Replay in Mission Control" opens
   `…&layout=v1`, the layout that trial used.
10. **Old links.** Open `/console?scenario=photo-board-decoy&seed=1001&method=surestop`, with no
    layout. It opens v1, shows a notice saying so, and the address gains `layout=v1`.
11. **Bad links.** Open `/console?layout=v3`. An error explains the accepted values; no room is
    built and Run is disabled.

## Limitations

- **Two zones for the occluded target.** In `occluded-target`, the need for a crate that hides the
  first route view, while the plant stays visible later and the crate stays off the route, limits
  where the plant can go. Over seeds 0–299 (current generator) it lands in:
  - the north-east strip in 72% of seeds;
  - the east-wall strip in 28%;
  - no other zone.

  Before phase 2 the split was 72 / 26 / 2.

  Seeds 0 and 17 move the plant only 0.72 m, the smallest move of any scenario. The furniture,
  start and light differ widely. A 2.4 m crate cap balanced the zones better (58% / 41%) but put
  the crate mid-room. I kept the 1.8 m cap, close to v1's "stands behind a crate" (0.87 m).
- **Fixed route.** The route is fixed and was written for v1. v2 keeps objects off it and requires
  observability, so some areas are never used for scenario objects: the east-room centre, the
  south-east for the occluded target, and the doorway.
- **Approximate checks.** Observability and occlusion are 2-D geometric checks.
  - Line of sight treats every footprint as full height, so a 0.8 m crate is treated as fully
    blocking.
  - They do not predict detection (3 of 18 decoy layouts were never detected).
  - Footprints use measured GLB bounds. The browser test bounds the gap to the world builder's grid
    at 1 cell.
- **v2 is unevaluated.** None of the calibration, held-out or headline results uses v2, and no
  statistical claim is made about it. The real-mission table is a smoke test on a handful of seeds.
- **Robot pose in the 3-D view.** The selected (past) frame's robot pose is still not shown in the
  scene (unchanged).

**Opt-in perception runs.** The 3 gap cases first ran as expected failures (`test.fail`), then,

**Unresolved.**

- **H2, the look-alike false arrival.** It is open by design in this phase; no verifier change was
  allowed.
- **Decoy detection gap.** Decoys that geometry says are in view are not always detected; the
  validator does not model detection. Possible next steps: require a closer or more frontal first
  view for decoys, or check decoy encounter with real perception before accepting a layout. Either
  changes which layouts are generated.
- **L5: cross-browser layout ids.** Ids agree between Node and Chromium (both V8). Other engines
  are untested.
- **L6: scene handed to the robot.** The robot-side sensor still receives a `THREE.Scene` with
  object names. This is pre-existing; no robot code reads the names.
- **M6: post-hoc criteria.** The "differ materially" criterion and the occluder cap were revised
  after observing failures in phase 1. Phase 2 did not change them.
- **Fallback in a real browser.** A forced fallback was tested at unit level (record, summary,
  export builder), not in a browser, because the console has no switch to force one.
